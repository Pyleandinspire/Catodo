# 阶段七开发笔记：Catodo 项目开发过程总结

## 写作日期

2026-06-06

## 一、项目概览

**Catodo** 是一款基于 Flutter 的跨平台任务管理应用，结合本地数据持久化、WebDAV 多端同步与多模型 AI 能力，旨在为用户提供轻量、灵活、智能的待办管理体验。

### 核心技术栈

| 类别       | 技术选型                                          |
| ---------- | ------------------------------------------------- |
| UI 框架    | Flutter 3.x + Material Design                     |
| 状态管理   | Riverpod                                          |
| 本地数据库 | Isar 3.x                                          |
| 网络层     | Dio                                               |
| 通知       | flutter_local_notifications                       |
| 持久化配置 | shared_preferences                                |
| 同步协议   | WebDAV                                            |
| AI 集成    | OpenAI 兼容 API（DeepSeek/豆包/GLM/Qwen/Kimi 等） |

## 三、关键技术总结

### 3.1 Isar 数据库实践

**优势**：

- 强类型 + 代码生成，几乎零运行时反射开销
- 原生支持 `watch()` 流，配合 Riverpod 实现响应式 UI
- 支持复合索引，查询性能优秀

**注意点**：

- `reminderTimes` 这类 `List<DateTime>` 字段在生成代码后必须在构造函数中显式赋值
- 软删除（`isDeleted`）字段配合 `updatedAt` 时间戳是同步的基础

### 3.2 通知调度模式

```dart
// 应用启动时
void initializeNotifications() async {
  await NotificationService().initialize();
  // 关键：重新调度所有未完成任务的提醒
  final tasks = await taskDao.getActiveTasks();
  for (final task in tasks) {
    for (final time in task.reminderTimes) {
      if (time.isAfter(DateTime.now())) {
        await scheduleNotification(task, time);
      }
    }
  }
}
```

**经验**：通知是一次性调度的，必须在应用启动时主动恢复，不能依赖系统持久化。

### 3.3 WebDAV 协议实现要点

**URL 拼接**：必须手动处理斜杠边界，不能依赖 Dio 的 `baseUrl` 相对路径解析

```dart
String buildUrl(String path) {
  final baseUrl = config.url.endsWith('/')
      ? config.url.substring(0, config.url.length - 1)
      : config.url;
  final cleanPath = path.startsWith('/') ? path : '/$path';
  return '$baseUrl$cleanPath';
}
```

**目录创建**：使用 MKCOL 方法，对 405 状态码（目录已存在）视为成功

```dart
if (response.statusCode == 201 ||
    response.statusCode == 204 ||
    response.statusCode == 405) {
  return true;
}
```

**错误处理**：所有失败场景必须打印请求 URL 和状态码，否则线上问题无从排查

**认证头**：必须在 `BaseOptions` 中初始化，不能在每个请求中重复设置，否则可能被覆盖

### 3.4 多模型 LLM 抽象设计

**核心思想**：所有国产大模型都兼容 OpenAI API 格式，因此采用 "预设配置 + 配置驱动" 而非 "多适配器" 模式。

**演进历程**：

1. **V1（笔记 05）**：`baseUrl + apiPath` 拆分设计，`supportsJsonMode` 区分 JSON 模式
2. **V2（笔记 06 Bug 修复）**：修复双版本路径问题，为 GLM/千问/豆包单独设 `apiPath`
3. **V3（当前）**：`apiUrl` 完整端点 URL，移除 `supportsJsonMode`，最大兼容性策略

```dart
// V3 最终设计
class LLMProvider {
  final String id;
  final String name;
  final String apiUrl;           // 完整端点 URL，如 https://api.openai.com/v1/chat/completions
  final String defaultModel;     // 仅作默认值，不硬编码模型列表
  final String description;
  final double defaultTemperature;
}
```

**最大兼容性策略**：

- 不发送 `response_format`（部分厂商不支持会报 400），改用 prompt 强制 JSON
- 宽容解析响应：兼容 `choices[0].message.content`、`output.text`、`data` 等格式
- 宽容解析 JSON：兼容 markdown 代码块包裹、多余文字、空白换行
- 动态获取模型列表：通过 `GET /models` 端点从厂商 API 获取，失败返回空列表（用户手动输入）
- 已知限制：豆包（火山引擎 Ark）数据面 API 不支持 `GET /models`

### 3.5 单元测试策略

- **可测试性设计**：内部辅助方法使用 `@visibleForTesting` 暴露
  ```dart
  @visibleForTesting
  String buildUrl(String path) { ... }
  ```
- **覆盖重点**：URL 拼接、配置有效性、边界情况（空值、末尾斜杠、相对/绝对路径）
- **测试组织**：按业务模块分组（`AIConfig URL 构建测试`、`WebDAVService URL 构建测试` 等）

### 3.6 AI Agent 设计

**核心思想**：通过 Prompt 指令协议让 LLM 返回结构化操作指令，客户端解析执行，实现"对话即操作"。

**方案选型**：Prompt 指令模式 > Function Calling > 混合模式。选择理由：所有厂商兼容、实现简单、复用现有架构。

**关键设计**：

- **指令协议**：LLM 返回 `{"reply": "...", "actions": [...]}`，9 种 Action 类型覆盖全部任务操作
- **上下文注入**：每次请求附带任务摘要（最多 50 个）+ 分组/标签列表，让 LLM "看到"当前状态
- **安全分层**：低风险操作（创建/加标签/分组/优先级）自动执行，高风险操作（删除/完成/更新）需用户确认
- **确认 UI**：黄色警告卡片，列出操作描述 + 确认/取消按钮

## 四、踩坑与教训

### 4.1 默认值陷阱

`LLMProvider` 的 `baseUrl` 默认空字符串看似合理，但当用户切换到 "自定义" 模式时，会导致 URL 变成相对路径。

**教训**：默认空值需要业务代码主动判断，或使用 `required` 强制传入。

### 4.2 双版本路径（已解决）

不同 LLM 提供商对 API 路径的设计不统一：

- OpenAI 风格：`baseUrl = https://api.openai.com`，`apiPath = /v1/chat/completions`
- 中国厂商风格：`baseUrl = https://open.bigmodel.cn/api/paas/v4`，`apiPath = /chat/completions`

**最终方案**：去掉 `baseUrl + apiPath` 的拆分设计，改为 `apiUrl`（完整端点 URL）。用户直接填写厂商提供的完整 API URL，预设提供商自动填入完整地址（如 `https://api.openai.com/v1/chat/completions`），所有提供商的 URL 字段均可编辑。彻底消除路径拼接问题。

### 4.3 response_format 不兼容（已解决）

部分厂商不支持 `response_format: {"type": "json_object"}` 参数，发送后直接返回 400 错误。

**最终方案**：不再发送 `response_format` 参数，改用 system prompt 强制要求 JSON 格式输出，并在解析时宽容处理（兼容 markdown 代码块包裹、多余文字等）。

### 4.4 模型名称硬编码过时（已解决）

各厂商模型更新频繁，硬编码的模型列表很快过时（如 DeepSeek 已从 `deepseek-chat` 更新到 `deepseek-v4-flash`）。

**最终方案**：移除 `models` 预设列表，通过 `GET /models` 端点从厂商 API 动态获取当前可用的模型列表。获取失败时返回空列表，用户手动输入模型名称，UI 显示红色提示"获取失败，请检查 API URL 和 API Key，或手动输入模型名称"。

**已知限制**：豆包（火山引擎 Ark）的数据面 API 不支持 `GET /models` 端点（返回 401），其模型列表需要通过管控面 API（HMAC-SHA256 鉴权）获取，当前不支持自动获取。

### 4.5 坚果云 WebDAV 限制

坚果云不允许直接在 `/dav/` 根目录创建文件，必须先 MKCOL 创建子目录。这是云盘服务对资源组织的限制。

**教训**：WebDAV 协议虽然标准，但服务端实现差异很大，需要为常见服务做兼容处理。

### 4.6 Dio 4xx 抛异常

Dio 默认对 4xx 状态码抛 DioException，导致原本依赖返回 `response.statusCode` 判断的逻辑永远走不到。

**教训**：业务关心的状态码差异（如区分文件不存在的 404）必须配置 `validateStatus`，或在 catch 块中精确处理。

### 4.7 错误日志不完整

最早的错误打印只有 `e.message`，导致同事调试时不知道请求的目标 URL 是什么。

**教训**：错误日志必须包含足够的上下文：请求 URL、状态码、关键参数。

### 4.8 Dart 级联操作符与 void 方法

`List.sort()` 返回 void，不能在级联中继续调用 `.join()`：

```dart
// 错误
groups.toList()..sort().join(', ')
// 修复
final sorted = groups.toList()..sort();
sorted.join(', ')
```

**教训**：Dart 的级联操作符 `..` 返回原对象，但 `sort()` 本身返回 void，两者混用会导致编译错误。

### 4.9 Agent 上下文 token 消耗

每次请求注入任务摘要会消耗大量 token，50 个任务约 2000-3000 token。

**教训**：上下文需要控制大小，未来可考虑只注入最近/最相关的任务，或让用户选择注入范围。

## 七、开发心得

1. **架构简单优于过度抽象**：多模型支持本可以做适配器模式，但实际所有 LLM 兼容 OpenAI，"配置驱动" 反而更清晰。

2. **错误日志是生产力**：详尽的日志在调试时能节省大量时间，特别是网络请求类问题。

3. **测试驱动修复**：每次修 Bug 都补一组测试，避免回归。本次 6 个 Bug 修复全部有对应测试覆盖。

4. **WebDAV 不要造轮子**：本来想直接用 webdav_client 库，但已有 Dio 依赖，自己实现协议反而能精细控制错误处理和日志。

5. **用户输入优先级最高**：预设值只是为了降低用户使用门槛，真正发请求时必须以用户输入为准。
