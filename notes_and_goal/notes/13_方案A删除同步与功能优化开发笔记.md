## 一、背景

用户反馈：通过 WebDAV 同步后，已删除的任务会在云端"复活"——删除操作无法跨设备传播。

## 二、问题根因分析

### 2.1 问题链路

```
用户删除任务 → isDeleted=true, updatedAt=now
                ↓
_getAllActiveTasks() 过滤掉 → 不传给 sync()
                ↓
远程任务 isDeleted=false → localMap 中找不到 → 当作"远程独有"下载
                ↓
mergedTasks 写回本地 → isDeleted 被覆盖为 false → 任务复活
```

### 2.2 三个环节的连锁缺陷

| 环节 | 文件 | 行号 | 问题 |
|------|------|------|------|
| 发送数据 | `task_list_screen.dart` | L277 | `getAllActiveTasks()` 过滤了 `isDeleted=true` 的任务 |
| 同步匹配 | `webdav_service.dart` | L268-L274 | 被删任务不在 localMap 中 → 被当作"远程独有"重新下载 |
| 冲突解决 | `webdav_service.dart` | L287-L296 | `_resolveConflict` 完全不处理 `isDeleted` 字段 |
| 写回本地 | `task_list_screen.dart` | L284-L287 | `updateTask` 用远程 `isDeleted=false` 覆盖本地 `isDeleted=true` |

## 四、核心修改：方案A 删除同步

### 4.1 设计原则

**删除优先策略**：任一方标记 `isDeleted=true` 即视为删除，传播到所有设备。双方都确认删除后从云端和本地彻底清除。

### 4.2 _resolveConflict 软删除处理

**文件**: `lib/services/webdav_service.dart`

```dart
/// 根据同步模式解决冲突（含软删除处理）
Task _resolveConflict(Task local, Task remote, SyncMode mode) {
  // 软删除优先处理：任一方删除即传播删除
  if (local.isDeleted || remote.isDeleted) {
    final deleted = local.isDeleted ? local : remote;
    deleted.isDeleted = true;
    return deleted;
  }

  // 双方都未删除 → 按原有模式处理
  switch (mode) {
    case SyncMode.autoMerge:
      return local.updatedAt.isAfter(remote.updatedAt) ? local : remote;
    case SyncMode.localFirst:
      return local;
    case SyncMode.remoteFirst:
      return remote;
  }
}
```

**关键设计决策**：
- 删除检查在 SyncMode 判断之前执行，确保删除操作不受同步模式影响
- 任一方 `isDeleted=true` 即返回标记删除的版本
- 双方都删除时返回 `isDeleted=true`（后续由 sync 方法过滤移除）

### 4.3 sync 方法过滤双方都删除的任务

**文件**: `lib/services/webdav_service.dart`

```dart
// 过滤双方都删除的任务（不再上传到云端）
mergedTasks.removeWhere((t) {
  if (t.syncId == null) return false;
  final local = localMap[t.syncId];
  final remote = remoteMap[t.syncId];
  return local != null && remote != null && local.isDeleted && remote.isDeleted;
});
```

**设计要点**：双方都确认删除后，任务从合并列表中移除，不再上传到云端，实现云端清理。

    .map((t) => t.syncId!)

    await dao.hardDeleteTask(localTask.id);
  }
}

### 4.5 多设备场景验证

```
设备一删除任务A → sync
  → 本地 isDeleted=true, 上传云端 isDeleted=true
设备二 sync
  → 远程 isDeleted=true, 本地 isDeleted=false
  → 删除优先 → 设备二标记 isDeleted=true
  → 云端保留 isDeleted=true
下次任一方 sync
  → 双方 isDeleted=true → 从合并列表移除
  → 云端不再包含该任务
  → 本地 hardDelete 清理
```

## 九、经验总结

### 9.1 软删除在分布式同步中的处理

软删除是本地数据库层面的设计，但在跨设备同步场景中，必须将 `isDeleted` 视为一种"状态变更"而非"数据移除"。同步时如果过滤掉已删除数据，会导致删除状态无法传播。

**核心原则**：同步时必须发送全量数据（含已删除），让删除状态像其他字段一样参与冲突解决。

### 9.2 冲突解决中的优先级设计

本次将"删除"的优先级置于"同步模式"之上——无论 autoMerge/localFirst/remoteFirst，只要任一方删除了，结果就是删除。这符合用户直觉：删除操作应该比修改操作有更高的优先级。

### 9.3 测试驱动的修复验证

通过 `@visibleForTesting` 暴露 `_resolveConflict` 等私有方法，可以在不启动完整同步流程的情况下，针对冲突解决逻辑编写精确的单元测试。8 个测试覆盖了删除传播的所有组合场景。

### 9.4 未来改进方向

- 考虑增加"撤销删除"功能（从软删除恢复）
- 考虑增加同步历史记录，便于排查同步冲突
- 考虑为过期任务添加视觉标识（如灰色或红色标记）
