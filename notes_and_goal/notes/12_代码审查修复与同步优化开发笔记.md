## 三、核心修改：syncId 引入与 WebDAV 同步重构

### 3.1 问题分析

原同步逻辑使用 Isar 自增 `id` 作为任务匹配的唯一标识：

```dart
// 旧逻辑：使用自增 id 匹配
final remoteMap = {for (var t in remoteTasks) t.id: t};
final localMap = {for (var t in localTasks) t.id: t};
```

**问题**：不同设备上 Isar 自增 id 从 0 开始，同一任务在两台设备上的 id 必然不同，导致同步匹配失败，所有任务都被当作"新任务"重复上传下载。

### 3.2 解决方案

在 `Task` 模型中添加 `syncId` 字段（UUID v4），作为跨设备唯一标识：

```dart
// lib/models/task.dart
@Index(unique: true, replace: true)
String? syncId;

static const _uuid = Uuid();

Task({...}) {
  this.syncId ??= _uuid.v4();  // 自动生成 UUID
}
```

**关键设计决策**：
- 使用 `@Index(unique: true, replace: true)` 确保数据库层面唯一约束，`replace: true` 在冲突时自动替换
- 构造函数中 `??=` 实现：有则用已有值（导入/同步场景），无则生成新 UUID（新建任务场景）
- 旧数据迁移：`sync` 方法中为没有 syncId 的旧任务自动生成 UUID

### 3.3 WebDAV 同步逻辑重构

```dart
// 新逻辑：使用 syncId 匹配
final remoteMap = <String, Task>{};
for (final t in remoteTasks) {
  if (t.syncId != null) remoteMap[t.syncId!] = t;
}
final localMap = <String, Task>{};
for (final t in localTasks) {
  if (t.syncId != null) localMap[t.syncId!] = t;
}
```

**同步流程**：
1. 为本地旧任务（无 syncId）自动生成 UUID
2. 下载远程数据，按 syncId 构建索引
3. 遍历本地任务：syncId 匹配到远程 → 冲突解决；未匹配 → 上传
4. 遍历远程任务：本地不存在的 → 下载
5. 合并结果上传回服务器

### 3.4 冲突解决策略

```dart
Task _resolveConflict(Task local, Task remote, SyncMode mode) {
  switch (mode) {
    case SyncMode.autoMerge:
      return local.updatedAt.isAfter(remote.updatedAt) ? local : remote;
    case SyncMode.localFirst:
      return local;
    case SyncMode.remoteFirst:
      return remote;
  }
}
```

**计数逻辑修复**：使用 `identical(winner, task)` 判断本地任务是否胜出，正确统计 `uploadedCount` 和 `downloadedCount`。

## 四、数据层配套修改

### 4.1 CatodoIO 导入导出

`catodo_io_service.dart` 的 `_taskToJson` 和 `_jsonToTask` 添加 syncId 字段，确保完整数据格式的导入导出完整性。

### 4.2 通知 ID 生成

通知 ID 从 `task.id * 10 + i` 改为 `Object.hash(task.syncId, i)`，避免跨设备 id 冲突导致通知 ID 重复。

```dart
// 旧：依赖自增 id
final notificationId = task.id * 10 + i;

// 新：基于 syncId 和索引生成确定性 ID
final notificationId = Object.hash(task.syncId, i);
```

同时 `cancelTaskReminder` 方法签名从 `cancelTaskReminder(int taskId)` 改为 `cancelTaskReminder(Task task)`，使用 syncId 计算取消 ID。

## 五、代码质量修复

### 5.1 提醒调度位置修复（C1 + ME1）

**问题**：`_rescheduleReminders` 在 `Consumer` 的 builder 中调用，每次 rebuild 都会触发，导致重复调度提醒。

**修复**：将 `CatodoApp` 从 `ConsumerWidget` 改为 `ConsumerStatefulWidget`，在 `initState` 中使用 `ref.listenManual` 监听 `isarProvider` 就绪后执行一次调度。

```dart
@override
void initState() {
  super.initState();
  ref.listenManual(isarProvider, (prev, next) {
    next.whenData((isar) => _rescheduleReminders(isar));
  });
}
```

### 5.2 Riverpod 性能优化

- **task_item.dart**: `_toggleComplete` 中 `ref.watch` 改为 `ref.read`，避免事件回调中建立不必要的监听关系
- **filter.dart**: 添加 `==` 和 `hashCode` 重写，避免 `StateNotifier` 因对象比较失败导致不必要的 Widget 重建

### 5.3 ICS 转义顺序修复

**问题**：`_unescapeIcs` 中先处理 `\n` 和 `,`，导致 `\\` 开头的双反斜杠被错误拆分。

**修复**：调整顺序，先 `\\\\` → `\\`，再 `\\,` → `,`，最后 `\\n` → `\n`。

```dart
static String _unescapeIcs(String s) {
  return s
      .replaceAll('\\\\', '\\')   // 1. 先处理双反斜杠
      .replaceAll('\\,', ',')       // 2. 再处理转义逗号
      .replaceAll('\\n', '\n');     // 3. 最后处理转义换行
}
```

## 八、经验总结

### 8.1 跨设备同步的核心问题

自增 ID 在分布式系统中天然不可靠。任何需要跨设备/跨实例同步的数据，都应使用全局唯一标识符（UUID）。这一原则适用于所有多端同步场景。

### 8.2 代码审查的发现价值

本次审查发现的 RadioListTile 弃用、ICS 转义顺序、ref.watch 滥用等问题，都是日常开发中容易忽略的细节。定期代码审查是保持代码质量的重要手段。

### 8.3 测试驱动修复

在修复过程中，先编写测试用例明确预期行为，再修改代码，最后验证测试通过。这种方式确保了修复的正确性，也为后续重构提供了安全网。
